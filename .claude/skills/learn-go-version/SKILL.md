# Go バージョンを勉強する手順（最新版 / 特定版 共通）

このリポジトリ（バージョン別 Go 学習リポジトリ）で、指定された Go バージョンを
「対象確定 → 情報取得 → 実機検証 → 教材化 → 解説 → ナレッジ化 → 移行分析 → README → コミット」の順に学習する。
過去の実施例は `go1.27.0/` を参照（このスキルはその流れを一般化したもの）。

## 絶対ルール（CLAUDE.md 準拠）

- **必ず日本語で回答する。** コード内コメント・README・ナレッジもすべて日本語。
- **必ず最新情報を取得してから答える。** 記憶や推測で機能を語らない（古い版でも公式ノートを引く）。
- **一次情報 + 実機で裏取り。** WebFetch の要約（小型モデル生成）は stdlib API 名を平気で
  ハルシネーションする。**必ず `go doc` と「実際に動くコード」で確認**してから教材に書く。
- **1 機能ずつ進める。** ユーザーは対話しながら学ぶので、勝手に全部作らず段階的に。

## 手順

### 0. 対象バージョンを確定する（最新 or 特定版）
- どのバージョンを学ぶかを最初に確定する。「最新」なら最新の安定版が何かを調べて `X.Y` を確定。
  「go1.26 を勉強したい」のように**特定版指定なら、その版を対象**にする（古い版でも手順は全く同じ）。
- 対象ディレクトリ名は `goX.Y.0`（例: `go1.26.0`）。既に空の README / go.mod がある場合もある（要確認）。
- 何を学ぶか（ユーザーが挙げる「気になる部分」を優先）。まず主要な言語/stdlib 変更を提示し着手順を相談。

### 1. 最新情報を取得（一次情報）
- `WebSearch` で全体像 → `WebFetch https://go.dev/doc/goX.Y`（**対象版**の公式リリースノート）で裏取り。
- 観点別に取る: 言語仕様 / 標準ライブラリ / ツールチェーン / ランタイム・メモリ・GC / 移行・非推奨。
- 二次情報（JetBrains, VictoriaMetrics tour 等）は補助。**数値・フラグ名は公式で確認**。
- 出典 URL は必ず控える（README の参考ソース表と回答末尾の Sources に使う）。

### 2. ツールチェーン準備（このディレクトリだけで対象版を使う）
- `goX.Y.0/go.mod` を用意。module パスは既存の命名に合わせる: `github.com/Taguchi-ivi/go_v/goX.Y.0`、
  `go` 行は `X.Y.0`。
- **`GOTOOLCHAIN` は `auto` にする**（`go env -w GOTOOLCHAIN=auto`）。各ディレクトリが自分の
  go.mod に従って toolchain を選ぶ。**特定版でも `auto` なら初回 `go` 実行で自動 DL される**
  （`go: downloading goX.Y.0`。古い版も新しい版も同様にダウンロードできる）。
  - ⚠️ **`go env -w GOTOOLCHAIN=goX.Y.0`（厳密ピン）をグローバルにやらない。** 全プロジェクト・
    別リポジトリまで対象版に強制してしまう。過去に一度これで事故った → `auto` に戻すのが正解。
- **IDE(gopls) は「対象版が今の gopls より新しいときだけ」再ビルドが要る**（古い版なら現行 gopls で足りる）。
  必要な場合: `GOTOOLCHAIN=goX.Y.0 go install golang.org/x/tools/gopls@latest` → エディタで言語サーバ再起動。
  `gopls version` と `go version $(which gopls)` で「対象版でビルドされたか」を確認。

### 3. 実機検証（最優先・ハルシネーション対策）
機能ごとに：
- `go doc <pkg>` / `go doc <pkg>.<Sym>` で **本物の API シグネチャ**を確認。
- `scratchpad` か `goX.Y.0/_probe/` に小さな検証コードを書いて **実行**し、コンパイラ/実行時の
  「本物の出力」で確認する。エラーになった構文は境界として記録（できる/できないを表にする）。
- 例: 言語機能なら「インターフェースに入るか」「reflect から見えるか」「method value/expression」
  などの境界を実際に試す。**検証が終わったら probe は消す**。

### 4. 教材化（動く main.go）
- `goX.Y.0/<機能名>/main.go` を作る（`camelCase` 例: `genericMethods`, `goroutineLeak`, `minorChanges`）。
- **after = 実際に動くコード、before = コメント**の形。冒頭にファイル概要コメント（何が変わったか/実行方法）。
- Go の慣習・周囲のコードに合わせた日本語コメント。テストが要る機能（synctest 等）は `main_test.go`。
- 作ったら必ず `go run ./<機能名>` / `go test ./<機能名> -v` で緑を確認。

### 5. 各トピックを解説する（今回一番価値が出た部分・この型で説明する）
教材を作ったら、ユーザーに**次の型で解説**する（実機で得た事実ベースで）:
1. **一言でいうと** … 何が変わったか 1〜2 行。
2. **何が問題だったか（旧版）→ 何ができるようになったか** … before/after を対比。
3. **境界（できる/できない）** … 実機で確かめた表（例: interface 不可 / reflect 不可 / method value 要 instantiation）。
4. **実務での勘所** … いつ使うと嬉しいか、選び方（例: uuid の V4 vs V7）、落とし穴。
5. **手元で確かめるコマンド** … `go run ./…` 等。
- 「深掘りしますか / 次に行きますか」で対話的に進める。

### 6. ナレッジ化（knowledge/）
- `goX.Y.0/knowledge/NN-topic.md`（`00-overview` から連番）に検証結果をまとめる。
  - 実機で得た表（できる/できない、before/after、ベンチ数値）、移行注意、`[[他ノード]]` リンク。
- `goX.Y.0/knowledge/README.md`（索引）に 1 行追加。対応する `../機能` へのリンクも。
- `00-overview.md` に「概要 + 移行チェックリスト（macOS 等プラットフォーム要件・非推奨・削除 GODEBUG）」。

### 7. モダナイズ（最新の書き方 / そのバージョンで使えるもの）
- `go tool fix help` で登録アナライザ一覧を取得。
- **そのバージョンで新規追加された分**を切り分ける（公式ノートの "new modernizers" と、
  新 API を狙うもの。多くは旧バージョンから gopls にあった既存分なので混同しない）。
- `go fix -diff ./...` に旧スタイルのコードを食わせ、**本物の before→after を採取**して
  `knowledge/` にカタログ化。適用は `go fix ./...`、個別は `go fix -<name> ./...`。

### 8. 移行分析（別プロジェクトを上げても大丈夫か）
- **オプトイン vs 強制**を実機で見極める。例: JSON v2 は `encoding/json/v2` を import した時だけ
  厳格化し、v1 API のままなら意味論は不変。「上げるだけで壊れる」と決めつけず probe で確認する。
- **旧↔新ツールチェーンでベンチ比較**して速度変化を数値で出す:
  - `scratchpad` に **別 go.mod（`go` 行を低め）**の module を作り、同一コードを
    `GOTOOLCHAIN=go(旧) go test -bench` と `GOTOOLCHAIN=goX.Y.0 go test -bench` で回す。
- プラットフォーム要件（最小 macOS 等）、削除 GODEBUG、`compress/flate` 出力バイト差などの
  「地雷」をチェックリスト化。ユーザーのスタック（例: gRPC は protobuf を使い encoding/json を
  通らない）に即して「実際に効くか」を答える。**誤解を招く記述を書いてしまったら証拠付きで訂正**。

### 9. README 更新
- `goX.Y.0/README.md`: 参考ソース表 / 気になる部分（学習対象一覧）/ 機能面以外のメモ（メモリ・速度・
  GC・互換性、数値とフラグ名つき）/ 実行コマンド / 移行メモ。
- ルート `README.md`: プロジェクト構成ツリーに `goX.Y.0/` を追加、学習内容セクション追加、参考資料追加。
  未学習バージョンがあれば TODO として明記。

### 10. 検証してコミット
- `go build ./...` / `go vet ./...` / `go test ./...` を **全部緑**にする。
- コミットはユーザーが求めたときだけ。`main` にいるなら**先にブランチを切る**。
- コミットメッセージ末尾に必ず:
  `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`

## 「最新の書き方」チェック（教材コードに適用）
- `interface{}` → `any` / 3節for → `for i := range n` / if-else → `min`/`max`。
- 並行の待ち合わせ → `wg.Go(func(){...})`（Go 1.25+、Add/Done 不要）。ループ変数は 1.22+ で反復ごと独立。
- 並行の結果集約は各 goroutine が別要素（`results[i]`）に書けば mutex 不要。**`go run -race` / `go test -race` で無競合を確認**する癖をつける。
- 迷ったら `go fix -diff ./...` で標準の推奨形を機械的に確認。
- ※ 対象が古い版なら、その版で存在する機能だけを使う（新しすぎる書き方を混ぜない）。

## よくある落とし穴（過去に踏んだ）
- WebFetch 要約の stdlib API は**信用しない**（`bytes.CutLast` 等は実在したが、実在しない関数も混ざる）。`go doc` 必須。
- `GOTOOLCHAIN` の**グローバル厳密ピン**は全体に波及する。`auto` を使う。
- gopls が対象版より古いと新構文が赤線（`method must have no type parameters` 等）。**対象版でビルドし直せば解消**、コード自体は正しい。
- `go build ./<dir>` で「output already exists and is a directory」は**バイナリ名がディレクトリ名と衝突しただけ**でコンパイルは成功。`go vet ./<dir>` で確認。
- cSpell の Unknown word 警告は無視してよい（スペル辞書の話）。

## 完了の定義
- 対象機能ごとに: 動く `main.go`（必要なら `_test.go`）+ 解説 + `knowledge/NN-*.md` + 索引更新。
- ルート/バージョン README 更新。`build`/`vet`/`test` 全緑。出典を回答に明記。
